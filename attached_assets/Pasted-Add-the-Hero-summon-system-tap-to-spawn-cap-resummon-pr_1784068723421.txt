Add the Hero summon system — tap-to-spawn, cap, resummon, promotion, and rare variant
What & Why
Heroes are the tap-summoned unit, distinct from Soldiers (auto-spawn, covered in the Sellswords task). The Core Climb Loop milestone already has a single placeholder tap-to-attack unit; this task formalizes it into the real system: a concurrent-hero cap governed by the Summon skill, resummon-on-death (not permanent loss), a title-based promotion track tied to the Hero Level Wall, and a rare stronger variant that can spawn instead of a normal hero.
Done looks like

Tapping the climb screen summons a Hero, up to a concurrent cap: Max Concurrent Heroes = Base Pool + 2 × Summon Skill Level
A Hero killed by an enemy becomes inactive and frees its summon slot — it is not permanently lost. Tapping again resummons into that freed slot.
A Heroes tab shows current/max concurrent heroes, current promotion title, and the Summon skill's level and upgrade cost
Promotion system: the Hero holds a single evolving title, not a multi-unit roster. Title advances at Hero level breakpoints 10 / 50 / 100 / 500 / 1,000, following: Recruit (starting title) → Blade Adept (10) → Vanguard (50) → Champion (100) → Legend (500) → Hero (1,000). Each promotion grants a large, one-time HP/Attack/Speed boost — this is the Hero Level Wall system referenced in planning; its breakpoint levels are confirmed, but the boost magnitude is not, so use a clearly-flagged placeholder multiplier (e.g. a large jump, tunable) rather than inventing a precise "real" number.
Every promotion tier and its title needs an ID separate from its display name, same as every other renamed system (e.g. hero_rank_1 → "Recruit", hero_rank_2 → "Blade Adept", etc.) — logic reads the ID/level, never the title string.
A rare stronger Hero variant can spawn instead of a normal Hero on tap, at a rate controlled by its own skill (mechanic equivalent to what the source game calls its "berserker summon" skill — do not reuse that name; give this variant and its skill original IDs and display names, same as every other renamed system)
Hero base stats (attack/HP) are placeholder values for now, clearly isolated in the engine's data layer (not inlined in formulas or logic) — same treatment as the existing Player base HP/damage placeholder, since no verified per-hero-type reference data exists yet. Flag clearly for later replacement, don't treat as final.
The Power Up skill's multiplier applies to Hero stats through the same shared multiplier logic already used for Soldiers — not a duplicated calculation
Hero state (current count, promotion tier, Summon level, variant-spawn skill level) persists via the existing AsyncStorage save

Skill ID requirement (applies to every skill in this task, and every skill going forward)
Give every skill and every promotion tier a permanent internal ID, separate from its display name — same ID/display split already used for gear items. All logic (formula lookups, state keys, save data, cross-system references like "the skill that scales Hero attack off Soldier attack") must reference the ID, never the display string. Renaming a skill's or a tier's display name later should only ever touch the display-name constants file, never a logic or formula file. This is the standing pattern for every skill built after this one too (Growth Speed, Doping, Rain of Gold, Warp, Ultimate Summon, Fame, etc.) — give each an ID up front even before its final display name is decided.
Out of scope

The Fame skill (hero attack scaling off total soldier attack) — this has a real dependency on Soldiers being implemented first; note it as a follow-up task once Soldiers state exists, don't build it against a guess. Reserve its ID now if convenient, but don't implement its logic yet.
Growth Speed, Doping, Rain of Gold, Warp, Ultimate Summon — separate skill tasks
The Soldier Level Wall and Tower Floor Wall systems — this task only implements the Hero Level Wall
